# 概要

AIエージェントに数時間から数日かかる仕事を任せると、モデルの性能だけでは足りない場面が増える。途中でコンテキストが尽きる、終わっていないのに終わったと言う、同じ失敗を繰り返す、といった失敗はモデルの外側で防ぐ必要がある。

モデルの外側にある仕組みをハーネスと呼び、それを設計する営みをハーネスエンジニアリングと呼ぶ。この記事では、2024年12月から2026年4月に公開されたAnthropic、OpenAI、martinfowler.comの資料をもとに、ハーネスの構成要素と設計の型を整理する。最後に、Claude Codeの機能との対応を示す。

この記事が扱うのは、エージェントを使う側が自分の用途のために組むハーネスである。モデルの学習やエージェント製品そのものの内部実装は扱わない。

# ハーネスとは何か

Birgitta Böckelerは「Agent = Model + Harness」と整理し、ハーネスをモデル以外のすべてとしている。システムプロンプト、ツール、ファイルやメモ、検査の仕組み、人の確認の入れ方が含まれる。

OpenAIは、手書きのコードを使わずにCodexだけで製品を作った5か月の実験を報告している。約100万行、約1,500件のPRを3人で出した結果、エンジニアの主な仕事は、コードを書くことから環境・意図・フィードバックの仕組みを設計することに移ったと述べている。

Anthropicは評価の文脈で、エージェントを評価するとは「ハーネスとモデルの組み合わせ」を評価することだとしている。同じモデルでも、ハーネスが変われば結果が変わる。

# なぜハーネスが要るのか

Anthropicは、長時間の作業を複数のコンテキストウィンドウにまたがって続けさせたときの失敗を、次のように報告している。

| 失敗 | 何が起きるか |
|---|---|
| 一度に全部やろうとする | 途中でコンテキストが尽き、作業が中途半端なまま次のセッションに渡る |
| 早く終わったと言う | 途中まで進んだ様子を見て、全体が終わったと判断する |
| 確かめずに完了にする | 単体テストや`curl`は通しても、端から端までは動いていない |
| 状況の把握に時間を使う | 前のセッションで何が起きたかを推測し、壊れた状態を直すのに時間を使う |

コンテキストが長くなるほど、モデルが中身を正確に思い出しにくくなる性質（context rot）も報告されている。コンテキストは限りのある資源であり、増やせば良くなるものではない。

マルチエージェントの調査システムでは、状態を持つエージェントの小さな誤りが連鎖して大きくなることも挙げられている。最初からやり直すと高くつくため、誤りが起きた地点から再開できる設計が要る。

# ガイドとセンサー

Böckelerは、ハーネスの制御を2つの向きと2つの性質で整理している。

| | 決定的（computational） | LLMの判断（inferential） |
|---|---|---|
| ガイド（行動の前に導く） | 型、テンプレート、スキャフォールド | 規約の文書、AGENTS.md、スキル |
| センサー（行動の後に確かめる） | テスト、リンター、型チェック、構造テスト | AIレビュー、LLMによる判定 |

ガイドだけでは、ルールが効いたかどうかが分からない。センサーだけでは、同じ失敗を毎回直すことになる。両方を組み合わせて、人が見る前の段階でエージェント自身が直せるようにする。

決定的なセンサーは速く、結果が揺れない。LLMの判断は遅く揺れるが、意味を見られる。速いものはコミットの前に、重いものは統合の後に回すと、品質の確認を前倒しにできる。

センサーの出力は、LLMが読んで直せる形にする。OpenAIはカスタムリンターのエラーメッセージに直し方を書き、エージェントのコンテキストに渡している。Anthropicのツール設計の記事も、エラーはコードではなく、具体的に何をどう直すかを返すよう勧めている。

# コンテキストの設計

Anthropicは、コンテキストの設計の指針を「望む結果を最も出しやすい、信号の強い最小のトークンの集合を探すこと」としている。

- システムプロンプトは、if-elseを並べた決め打ちでも、曖昧な一般論でもない高さで書く。
- 例は、例外を網羅した規則のリストではなく、典型的な例を少数選ぶ。
- 情報は最初に全部入れず、ファイルのパスやリンクだけを持たせ、必要なときにツールで読ませる。

OpenAIは、大きなAGENTS.mdが失敗した理由を次の4つとしている。

- コンテキストを圧迫する
- すべてが重要だと、何も重要でなくなる
- すぐ古くなる
- 機械的に確かめにくい

そこで約100行のAGENTS.mdを目次にし、構造化した`docs/`を記録の置き場にした。「取扱説明書ではなく地図を渡す」という考え方である。

Agent Skillsも同じ考え方で作られている。起動時は名前と説明だけを読み、関係するときに本文を、さらに必要なときに同梱のファイルを読む。段階的に開示するので、多くのスキルを置いてもコンテキストを圧迫しにくい。

Claude Codeのドキュメントは、CLAUDE.mdに書くのは「コードを読んでも分からないこと」だけにするよう勧めている。作業を確かめるコマンド、誤解を招くコードの場所、リポジトリにない決定がその例である。

# 状態とメモの持ち方

コンテキストウィンドウをまたぐ作業では、前のセッションの記憶が無い。Anthropicは、交代勤務のエンジニアが前の勤務の記憶なしに出勤してくる状況にたとえている。

Anthropicの長時間エージェントのハーネスは、3つで状態を引き継ぐ。

1. やることの一覧をJSONで持つ。最初はすべて未達にし、エージェントが変えてよいのは合否の欄だけにする。
2. 進捗のメモをテキストで持ち、セッションの終わりに書き足す。
3. セッションの区切りでgitにコミットし、壊したら戻せるようにする。

一覧の形式は、Markdownと比べてモデルによる不適切な書き換えが少なかったJSONを選んだ。セッションの始めには、作業ディレクトリ、進捗のメモ、`git log`、一覧の順に読み、基本の動作を確かめてから次の作業に入る。

OpenAIは、計画を第一級の成果物として扱う。複雑な作業は、進捗と意思決定のログを含む実行計画としてリポジトリに入れる。Slackや人の頭の中にある知識は、エージェントには存在しないのと同じだからである。

Anthropicのマルチエージェントの調査システムは、計画を外部のメモリに保存する。サブエージェントは成果物を外部に書き、軽い参照だけをリードに返す。すべてをリード経由で伝えると、伝言ゲームのように情報が欠けるためである。

# 作業の分け方

## 1回で1つ進める

Anthropicの長時間エージェントのハーネスで最も効いたのは、1回のセッションで1つの機能だけを進めさせることだった。終わったら、次のセッションがすぐ着手できる状態にしてから止める。

## ワークフローとエージェント

Anthropicは、決められた経路でLLMを動かすものを「ワークフロー」、LLMが自分で手順を決めるものを「エージェント」と分けている。最も単純な解から始め、成果が上がると示せたときだけ複雑にすることを勧めている。

| 型 | 内容 | 向く場面 |
|---|---|---|
| 直列 | 前の出力を次に渡す。途中に検査のゲートを置ける | 固定の手順に分けられる。例: 骨子を作り、条件を満たすか確かめてから本文を書く |
| 振り分け | 入力を分類して専用の処理に回す | 種類ごとに扱いを分けたい |
| 並列 | 分割して同時に処理するか、同じことを複数回して多数決する | 速さが欲しい、複数の視点が欲しい |
| オーケストレーターとワーカー | 中心のLLMがタスクを分けて任せ、結果をまとめる | 必要な作業を前もって決められない |
| 評価と改善の繰り返し | 生成役と評価役を分けて往復する | 評価の基準がはっきりしている |

## サブエージェントの使いどころ

マルチエージェントの調査システムでは、リードが計画を立て、並列のサブエージェントに検索を任せる構成が、単一のエージェントより社内評価で90.2%高い性能を出した。一方で、トークンはチャットの約15倍を使う。向くのは、価値が高く、並列化しやすく、1つのコンテキストで収まらない調査である。

委任するときは、目的、出力の形、使う情報源、作業の境界を明示する。短い指示だけだと、作業の重複や漏れが起きた。

Claude Codeのドキュメントは、サブエージェントで得られるのは「並列化か新しい目」であって、賢い答えではないとしている。向くのは、独立した作業の並列化、長い出力をメインの会話から外すこと、書いた経緯を知らないレビュアー、ツールを絞った作業である。

サブエージェントは会話の履歴を持たずに始まる。守らせたい規則は、委任の指示の中で言い直す必要がある。Claude Codeでは、人に選択肢つきで質問する`AskUserQuestion`はサブエージェントから使えない。人への質問はメインの会話でまとめて行う設計になる。

# 決定的に強制する

プロンプトに書いた指示は、守られないことがある。Claude Codeのドキュメントは、CLAUDE.mdで何度強調しても守られない行はhookに移すよう勧めている。逆に、好みにすぎないhookは消してモデルに任せる。

hookは、Claude Codeのライフサイクルの決まった時点で自動的に実行される処理である。

- `PreToolUse`で終了コード2を返すと、そのツールの呼び出しを止め、標準エラーの内容が理由としてモデルに返る。
- `Stop`で停止を止めると、理由が次の指示になり、作業を続けさせられる。テストが通るまで終わらせない、といった使い方ができる。
- `SessionStart`はセッションの再開時にも動くので、最新の状態を差し込むのに使える。

OpenAIは、ドキュメントでは守られなかったルールをコードに昇格させ、カスタムリンターと構造テストで強制した。依存の向き、命名、ファイルの大きさといった不変条件を、細部の管理の代わりに機械で守らせている。

# 人の関わり

ハーネスは人の関わりをなくすものではない。Böckelerは、良いハーネスは人の入力を最も重要なところへ向けるものだとしている。

## ステアリングループ

人の仕事は、同じ問題が繰り返されたらハーネスを直すことである。ガイドを足して起きにくくするか、センサーを足して早く見つける。その作業にもAIを使える。

Anthropicのスキルの記事も、作業中にうまくいったやり方と失敗を、エージェント自身にスキルへ書き戻させることを勧めている。必要な文脈を前もって予想するより、実際に要ったものを残すほうが確かである。

## 人に残すこと

Claude Codeのドキュメントは、無人で動かす前に次の5つを決めるよう求めている。

1. 完了の形が決まっているか（条件、仕様のファイル、通すべきテスト）
2. 自分の作業を確かめられるか（テスト、Stop hook、レビューの手順）
3. 何に触れてよいか（権限、サンドボックス、pushしてよいブランチ）
4. 何が止めるか（最大のターン数、予算の上限）
5. 結果がどこへ行き、誰が承認するか（PR、マージやデプロイの承認者）

人に残るのは、始めること、今回の完了を決めること、最後にマージを承認することである。

## 確かめるのは人の目だけではない

OpenAIは、レビューのほとんどをエージェント同士に移した。人は優先順位を決め、利用者の声を受け入れ基準に直し、結果を確かめる。判断が要るときだけエージェントが人に上げる。ただし、このリポジトリの構造に強く依存した結果であり、一般化できるとは考えるべきでないと注意している。

Böckelerは、問題の誤診断、過剰な設計、指示の取り違えは、どのセンサーも確実には捕まえないと指摘している。最初に何を望むかを人がはっきりさせない限り、正しさはどのセンサーの守備範囲にも入らない。

# 評価

Anthropicは、エージェントの評価を次の要素で整理している。

- 採点者は3種類ある。コードは速く客観的だが、形の違いに弱い。モデルは柔軟だが、人の判断に合わせた較正が要る。人は最も信頼できるが、高く遅い。できるだけ決定的な採点を使う。
- 採点するのは、どう進んだかではなく、何を作ったかである。ツールを呼んだ順序の検査は壊れやすい。
- 早く小さく始める。実際の失敗から集めた20〜50問で十分であり、初期は変更の効果が大きいので少数でも差が見える。
- 結果の揺れを測る。`pass@k`は`k`回のうち一度でも成功する確率、`pass^k`は`k`回すべて成功する確率である。1回75%なら、3回すべて成功するのは約42%になる。
- トランスクリプトを読む。読むまでは、点数を額面どおりに受け取らない。
- 自動の評価は層の一つにすぎない。本番の監視、利用者の声、人のレビューと組み合わせる。

マルチエージェントの調査システムでも、約20問から評価を始め、LLMによる判定を事実の正確さ、引用の正確さ、網羅性、情報源の質、ツールの効率のルーブリックで行った。それでも人の手動テストは欠かせなかった。初期のエージェントが権威ある情報源よりSEO向けのサイトを選び続けていたのを見つけたのは人である。

Böckelerは、センサーが鳴らないのは品質が高いからなのか、検出できていないからなのかが分からないという問いを残している。ハーネス自体の品質をどう測るかは、まだ決まった方法が無い。

# Claude Codeで組むときの対応

2026年11月時点のClaude Codeの機能と、ここまでの型の対応を示す。

| 型 | Claude Codeの機能 |
|---|---|
| 常に読ませる文脈 | `CLAUDE.md`（コードを読んでも分からないことだけを書く） |
| 段階的に読ませる手順と型 | スキル（`.claude/skills/<名前>/SKILL.md`）。副作用のある手順は`disable-model-invocation: true`で人が呼んだときだけ動かす |
| 文脈を分けた作業 | サブエージェント（`.claude/agents/<名前>.md`）。`tools`で使えるツールを絞る |
| 決定的な強制 | hook（`PreToolUse`、`Stop`、`SessionStart`）と権限のdenyルール |
| 状態とメモ | リポジトリのファイルとgit。サブエージェントは`memory`で会話をまたぐメモを持てる |
| 無人の実行 | `claude -p`、`--allowedTools`、`--permission-mode dontAsk`、`--max-turns`、`--max-budget-usd` |
| 再開 | `--resume`と`--continue` |

# 設計の指針

ここまでの資料から、ハーネスを組むときの指針をまとめる。

1. 最も単純な構成から始め、評価で効果を確かめてから複雑にする。
2. 1回の実行で進めるのは1つにし、次の実行がすぐ始められる状態で止める。
3. 状態は書き換えにくい構造化データ、経緯はメモ、区切りはgitで残す。
4. コンテキストには地図だけを置き、詳細は必要なときに読ませる。
5. 守らせたい規則は、プロンプトではなくhookやリンターで強制する。検査の出力には直し方を書く。
6. サブエージェントは並列化と新しい目のために使い、人への質問はメインの会話にまとめる。
7. 人は完了の定義と、取り消せない操作の承認に関わる。同じ失敗が繰り返されたらハーネスを直す。
8. 評価は少数の実例から始め、結果より先にトランスクリプトを読む。

# まとめ

- ハーネスはモデル以外のすべてであり、同じモデルでもハーネスで結果が変わる。
- 長時間の作業では、やりすぎ・早すぎる完了の宣言・確認なしの完了が起きやすい。1回で1つ進め、状態を外に書き、gitで区切って防ぐ。
- 制御は、行動の前に導くガイドと、行動の後に確かめるセンサーの組み合わせで設計する。決定的なものとLLMの判断によるものを使い分ける。
- 人の関わりをなくすのではなく、完了の定義、承認、ハーネスの改善に集める。
- 評価は少数の実例から始め、作った結果を採点する。ハーネス自体の品質の測り方は、まだ確立していない。
