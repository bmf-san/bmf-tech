# 概要

認可基盤の話になると、「全社の権限を一か所で管理する基盤を作る」か「各アプリに任せる」かの二択で語られることがある。実際にはその間に選択肢がある。たとえば、判定は各アプリに残したまま、トークンや監査ログの規約だけを揃えることもできる。

本記事では、組織にどれだけの認可基盤が要るかを決めるための材料を整理する。この記事でわかることは次のとおり。

- 認可基盤が組織とアーキテクチャの全体に及ぶ理由と、それでも一か所に集めない理由
- 横断で揃えるものと、各業務ドメインに任せるものの線引き
- どこまで要るかを決める判断の軸と、今起きている問題からの見方
- 共通の規約、判定の外部化、統制の仕組みという打ち手と、作らない方がよいサイン

認可とは何か、認証との違い、IAMのサブドメインの全体像は[認可とは？認証との違いとIAMのサブドメインで見る全体像](/ja/posts/authorization-domain-iam-subdomains/)が扱う。本記事はそれを前提として、組織として作る範囲に絞る。

本記事の打ち手の分け方や判断の軸は筆者の整理であり、標準化された判断基準があるわけではない。

先に全体像を示す。


# 認可基盤は組織とアーキテクチャの全体に及ぶ

認可の仕組みは、特定のチームやサービスの中に閉じない。アーキテクチャと組織の両面から、その理由を見る。

## アーキテクチャ: すべてのコンポーネントが同じ関心事を持つ

認可は、保護する資源へのすべてのリクエストで起きる。認証は入口で一度確かめれば、その結果をトークンに載せて運べる。一方、認可は「この主体が、この資源に、この操作をしてよいか」を資源ごとに問う。そのため、ゲートウェイから各サービス、データ層まで、保護する資源のある場所すべてに強制点（PEP、Policy Enforcement Point）が要る。

委譲もサービスをまたいで連鎖する。ユーザーからエージェント、MCPサーバ、業務APIへと、権限はサービスをまたいで運ばれる。トークンの宛先の設計、スコープの体系、トークンの取り直し方、ユーザーとエージェントの記録の仕方が揃っていないと、どこか1か所の緩い実装が全体の穴になる。受け取ったトークンをそのまま次のサービスへ中継する実装は、その一例である。

さらに、認可は後から変えにくく、止まると全体が止まる。判定を各アプリの中で行うと、認可のロジックは各所のコードに埋め込まれていく。そのため、権限のモデルを変えるときは、すべてのサービスに手が入る。逆に判定を外部化すると、判定サービスの障害がすべての機能を止めうる。判定できないときは通す（fail-open）のではなく止める（fail-closed）のが原則なので、判定サービスの可用性が全体の可用性を左右する。どちらに倒しても、影響範囲はアーキテクチャ全体になる。

どのコンポーネントも同じ関心事を持つので、強制の置き方やトークンの扱いを横断で揃える価値は大きい。ただし、すべてを1か所に集めるわけではない。何を揃え、何を各ドメインに任せるかは次の節で扱う。PEPを要求の経路のどこに置くかは[認可基盤のアーキテクチャと設計判断](/ja/posts/authorization-platform-architecture-decisions/)で扱う。サービス間の文脈の伝播は[ワークロードアイデンティティの標準化](/ja/posts/workload-identity-wimse-transaction-tokens/)、エージェントの委譲は[AIエージェントで認可の何が変わるか](/ja/posts/authorization-for-ai-agents/)で扱う。

## 組織: 1つのチームでは決めきれない

認可に関わる決定の持ち主は、組織の中に分散している。

まず、権限の「意味」は各業務ドメインにある。「この請求書を承認してよいか」の意味を知っているのは、その業務を担うチームだけである。認可基盤は判定の仕組みを提供できるが、何を許すかはすべての業務ドメインとすり合わせる必要がある。認可がドメインルールの塊であることは、[アーキテクチャ設計における共通化の罠](/ja/posts/abstraction-trap-in-architecture/)でも触れた。

次に、判定に必要な情報は組織中から集まる。

| 情報 | 主な出どころ |
|---|---|
| 主体の属性（所属、役職、雇用形態） | 人事システム、ディレクトリ |
| 権限の割り当て | 承認者、管理者（アクセスガバナンス） |
| リスクシグナル | セキュリティ部門、検知の仕組み |
| 契約の状態（プラン、契約期間） | 契約管理 |
| 資源の属性（所有者、公開範囲、状態） | 各業務ドメイン |

認可は、これらが合流する地点になる。どの情報を誰が持ち、どの鮮度で判定に届けるかは、1つのチームでは決めきれない。

最後に、統制は組織のプロセスそのものである。誰が権限を与えられるか、職務分掌、定期的な棚卸し、退職時の権限の剥奪は、組織構造や内部統制に直結する。退職者の権限を全システムから確実に消せるかは、技術だけでは決まらない。組織横断の仕組みで決まる。

つまり、認可基盤は技術の部品としては作れても、それだけでは足りない。何を許すか、どの情報をどの鮮度で届けるか、誰が統制するかは、複数の部門の役割分担と合意がないと決まらない。認可基盤は技術の境界だけでなく、部門の境界もまたぐ。

# 一か所に集めない: 横断で揃えるものと各ドメインに任せるもの

ここまでの理由から「認可は全社で一元管理すべき」と考えたくなる。しかし、それは2つ目の理由（権限の意味は各ドメインにある）とぶつかる。中央の基盤チームがすべての業務の権限の意味を抱え込むと、基盤チームがボトルネックになりやすく、抱えた業務知識も古くなりやすい。

そこで、**仕組みと契約は横断で揃え、意味は各ドメインに置く**。

| 横断で揃えるもの（基盤が持つ） | 各業務ドメインが持つもの |
|---|---|
| トークンの形式、宛先とスコープの設計規約、委譲の運び方 | 資源と操作の定義、業務上のルール |
| 判定APIの契約（AuthZENなど）とポリシーの書き方 | 自分のドメインのポリシーの中身 |
| 監査ログの形式、失効の手段、継続評価の配信 | ポリシーのテストと変更 |
| ガードレール（どのドメインでも破ってはいけない制約） | ガードレールの中での判断 |

ガードレールは、業務の意味を問わず、すべてのドメインが守る制約である。たとえば「テナントをまたいだ参照は許可しない」「判定できないときは拒否する」「特権操作は必ず監査ログに残す」といったものがこれにあたる。

```mermaid
flowchart TB
  subgraph Shared["横断（基盤が持つ）"]
    T["トークンの形式・宛先とスコープの規約・委譲の運び方"]
    API["判定APIの契約・ポリシーの書き方"]
    LOG["監査ログの形式・失効・継続評価"]
    G["ガードレール"]
  end
  subgraph DomainA["業務ドメインA"]
    PA["資源と操作の定義<br/>ポリシーの中身とテスト"]
  end
  subgraph DomainB["業務ドメインB"]
    PB["資源と操作の定義<br/>ポリシーの中身とテスト"]
  end
  Shared --> DomainA
  Shared --> DomainB
```

認証はIdPにほぼ一元化できるが、認可はそうできない。「誰か」には組織全体で1つの答えを出せるが、「何をしてよいか」の答えは業務ごとに違うからである。この違いがあるので、認可基盤は組織全体に及びながら、組織全体で分担して持つものになる。

共通基盤を作るかどうかの一般的な条件（支援・汎用サブドメインであること、複数チームからの再利用、継続的なオーナーシップなど）は、[プラットフォームの成立条件](/ja/posts/platform-viability-conditions/)で整理した。認可基盤もこの条件に照らせるが、権限の意味まで基盤に入れるとコアドメインの知識を抱え込むことになる。上の表の線引きは、基盤を支援・汎用の側にとどめるための線でもある。

# どこまで要るかを判断する

認可基盤は「必要か、不要か」の二択ではない。何もしなければ、各アプリがそれぞれのコードで判定する。そこに加える打ち手として、本記事では次の3つを扱う。

| 打ち手 | 中身 |
|---|---|
| 共通の規約とライブラリ | トークンの形式、宛先とスコープの体系、監査ログの形式、失効の手段を全社で揃える。判定は各アプリのまま |
| 判定の外部化 | 判定エンジン（PDP、Policy Decision Point）を共通化し、ポリシーをコードで管理する。ポリシーの中身は各ドメインが持つ |
| 統制の仕組み | 申請・承認、棚卸し、継続評価、委譲の連鎖の管理を揃える |

3つは順に上る段階ではなく、必要なものを選んで加える。ただし、判定の外部化は共通の規約を前提にする。PDPは、揃えたトークンの形式や監査ログの形式を前提に動く。共通の規約なしにPDPを入れると、PEPごとに主体の表し方やログの形式が違ったままになり、外部化の利点である一貫性と監査が得にくい。

判定の外部化は、凝集度と結合度の問題として見るとわかりやすい。各アプリに散らばっていた権限のルールをポリシーとして1か所に集め、凝集度を高める。アプリが依存するのは判定APIの契約だけになり、アプリとルールの結合度が下がる。そのため、ルールの変更がポリシーの中で閉じ、アプリのリリースと切り離せる。代わりに、PDPをネットワーク越しに呼ぶなら、判定の往復による遅延と、PDPの可用性への依存を負う。

PEPとPDPの役割とモデルの選び方は[認可のアーキテクチャとモデル、エンジンの選び方](/ja/posts/authorization-architecture-models-engines/)で扱う。PEPとPDPの配置と非機能の設計は[認可基盤のアーキテクチャと設計判断](/ja/posts/authorization-platform-architecture-decisions/)で、PEPとPDPの間をつなぐ標準は[AuthZEN Authorization APIとは](/ja/posts/authzen-authorization-api/)で扱う。

## 判断の軸

| 軸 | 基盤が必要になる方向 | 基盤がなくても回る方向 |
|---|---|---|
| 規模と横断性 | 認可が必要なアプリやサービスが多く、同じルールを複数のアプリに効かせたい | アプリが少なく、ルールがアプリごとに閉じている |
| 権限モデルの複雑さ | 条件付きの許可（時刻、金額、リスク）、共有・階層・継承の関係、顧客が自分でロールを作る、委譲がある | 固定の数ロールで足りる |
| 変更の頻度と、変える人 | ポリシーの変更が頻繁で、開発者以外（業務の管理者、顧客）が変えたい | 変更が少なく、変えるのは開発者だけ |
| 統制と規制の要件 | 監査の証跡、職務分掌、定期的な棚卸し、「なぜ許可したか」の説明が求められる | 監査の要求が軽い |
| 主体の多様さ | 人だけでなく、ワークロード、外部パートナー、AIエージェントがあり、委譲が連鎖する | 主体はほぼ人だけ |
| 一貫性の要求 | 複数のプロダクトで同じ人の権限を揃えたい。退職や権限変更を全システムにすぐ反映したい | プロダクトが1つで、反映の遅れが問題にならない |
| 組織の能力とコスト | 基盤を運用するチームがあり、判定サービスを高可用に保てる（または買える） | 運用できる人がいない。判定の往復による遅延や、可用性を下げるリスクを負えない |

最後の「組織の能力とコスト」は、ほかの軸と性質が違う。ほかの軸は必要性を示し、この軸は実現の可能性を示す。必要性が強くても能力が足りないなら、打ち手を絞る、またはマネージドサービスを使うといった選択肢を検討する。

権限モデルの選び方（RBAC、ABAC、ReBACなど）は[認可のアーキテクチャとモデル、エンジンの選び方](/ja/posts/authorization-architecture-models-engines/)で扱う。アプリ単位の権限設計（機能スコープとデータスコープなど）は[権限管理の設計](/ja/posts/permission-management-design/)にまとめた。

## 今起きている問題から判断する

軸は将来の要件を含めて考えるものだが、今起きている問題からも判断できる。次のような問題が起きていれば、打ち手を加える時期に来ている。

- 認可のコードが各アプリにコピーされていて、挙動がアプリごとに違う
- 認可の欠陥（他人のデータが見えるなど）が繰り返し起きている
- ロールの追加や権限の変更に、毎回開発とリリースが要る
- 「この資源を見られるのは誰か」に答えられない。監査のたびに人手で調べている
- 権限の申請がチケットとスプレッドシートで回っている

それぞれの問題が、どの軸とどの打ち手に関係するかの目安は次のとおり。

| 起きている問題 | 関係する軸 | 効きやすい打ち手 |
|---|---|---|
| 認可のコードがコピーされ、挙動が違う | 規模と横断性 | 共通の規約とライブラリ |
| 認可の欠陥が繰り返し起きる | 規模と横断性、権限モデルの複雑さ | 共通の規約とライブラリ、判定の外部化 |
| 権限の変更に開発とリリースが要る | 変更の頻度と、変える人 | 判定の外部化 |
| 誰が見られるかに答えられない | 統制と規制の要件 | 判定の外部化、統制の仕組み |
| 申請がチケットとスプレッドシート | 統制と規制の要件 | 統制の仕組み |

打ち手を加えるときに、全ドメインを一度に移す必要はない。問題の大きいドメインから移し、横断の契約はそのつど固めていく方が、基盤が実際の要件から離れにくいと筆者は考える。

freeeが専任のチームで権限管理基盤を開発・運用している事例（2023〜2024年公開の記事と発表資料）は、[権限管理基盤についての事例](/ja/posts/permission-management-case-study/)にまとめた。

## 共通の規約は早めに揃える

アプリやチームが複数あるなら、共通の規約は早い時期から揃えておく方がよいと筆者は考える。トークンや監査ログの扱いはチーム間の共通の契約である。基盤チームがいなくても規約として揃えておかないと、後から統一するのが重くなりやすい。

共通の規約で揃える対象の多く（トークンの形式、宛先とスコープ、失効）はOAuthとその周辺の標準で表せる。どの標準が何を決めるかは[認可基盤から見たOAuthと周辺標準の地図](/ja/posts/oauth-standards-map-authorization-platform/)で整理する。

# 作らない方がよいサイン

判定の外部化や統制の仕組みを入れるべきでない状況もある。

- プロダクトが1つで、ロールも少なく安定している
- 判定を外に出すことによる遅延や、判定サービスが止まったときに全体が止まるリスクの方が大きい
- 基盤を作っても、各チームには使うインセンティブがない（結局アプリ内で判定し続ける）

早すぎる基盤化は、利点が出る前に、可用性のリスクと運用の負担を増やしやすい。3つ目のサインは、[プラットフォームの成立条件](/ja/posts/platform-viability-conditions/)の「複数チーム／複数プロダクトから再利用される」という条件を満たせない状態でもある。

ただし、基盤を作らないことは何もしないことではない。前節のとおり、アプリやチームが複数あるなら、共通の規約は早めに揃えておく方がよい。作らない判断の対象は、主に判定の外部化と統制の仕組みである。

# まとめ

- 認可は保護する資源のある場所すべてで起き、意味は各業務ドメインにあり、材料は組織中から集まる。そのため認可基盤は組織とアーキテクチャの全体に及ぶ
- それでも一か所には集めない。仕組みと契約（トークン、判定APIの契約、監査ログ、失効、ガードレール）は横断で揃え、意味（資源と操作、ポリシーの中身）は各ドメインに置く
- 認可基盤は要否の二択ではない。各アプリでの実装に、共通の規約とライブラリ、判定の外部化、統制の仕組みのうち必要なものを加える。判定の外部化は共通の規約を前提にする
- 判断の軸は規模と横断性、権限モデルの複雑さ、変更の頻度、統制、主体の多様さ、一貫性、組織の能力の7つで、今起きている問題からも判断できる
- アプリやチームが複数あるなら、共通の規約は早めに揃える方がよいと筆者は考える。プロダクトが1つでロールも少なく安定している、遅延と可用性のリスクの方が大きい、使われる見込みがない、といったサインがあれば判定の外部化や統制の仕組みは作らない方がよい
